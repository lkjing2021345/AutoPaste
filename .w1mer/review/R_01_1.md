**(c) 超限粘贴契约（M5）——契约落地，但边界提示有 bug。**
实现改成“截断到 MAX_PAYLOAD + 排空到终止序列 + stderr 提示”
（`autopaste.py:1016-1058`）：
- 终止序列 `\x1b[201~` 在正常路径由 `endswith` 检测并删除；超限后进入
  `_discard_paste_tail()` 继续读到终止序列，**最多再读 MAX_PAYLOAD 字节**；
- 载荷截断到恰好 MAX_PAYLOAD（旧实现返回 MAX+1 并把终止序列留在流里，
  正是“REPL 凭空输入 `[201~`”的根因）；
- 测试三条：恰好上限不截断、超限只保留 limit 字节、超限后终止序列被消费且
  `tail\n` 原样留在流中 + stderr 含“已截断并丢弃”（`test_lineeditor.py:82-119`）。
  第三条用 `os.read(fd, 64)` 直接验证“残留字节不会被回灌”，是真断言。
- **Minor m1（新引入的边界 bug）**：当载荷**恰好等于 MAX_PAYLOAD** 且带终止
  序列时，循环在第 `MAX+5` 个字节（= 上限 + 终止序列前 5 字节 `ESC [ 2 0 1`）
  处先命中 `len(data) > MAX_PAYLOAD + 4`（`:1038`），`endswith` 因缺 `~` 为假
  → `overflow=True` → 打出“已截断并丢弃剩余部分”，随后 drain 读掉 `~`、
  `del data[MAX_PAYLOAD:]` 只删掉 5 个终止符字节，**载荷本身完好**。
  即：数据不丢，但注释里“恰好等于上限不算超限”的承诺被破坏，用户会看到
  与实际不符的截断警告。测试 `test_paste_at_exact_limit_is_not_truncated` 只断言
  文本，没有断言 stderr 不含该警告，因此抓不到（这是“测试没覆盖到自己刚写的
  边界”的典型）。建议把阈值放到 `MAX_PAYLOAD + 5`（或先判 `endswith` 再判
  超限，并把终止序列在超限分支也识别掉），并给该用例补
  `assertNotIn("已截断", err)`。
- **Nit n2**：drain 上限为 MAX_PAYLOAD，因此 >≈2 MiB 的粘贴可能在排空配额用尽
  后把剩余字节留给 REPL 当普通输入（`[201~` 残留在极端情况下仍可能出现），
  而提示仍说“已丢弃”。属已文档化的取舍，建议在文档/提示里写清“最多再丢弃
  1 MiB”即可。
- 用户粘贴丢字符的风险：截断到 1 MiB 有明确 stderr 提示，且 REPL 仍需用户
  回车才提交，不构成静默丢字；相比旧实现（多读 1 字节且把终止序列留在流里）
  是净改善。

### 4. 02.1.1 ydotool `-e` 能力探测（R_02_1 N1）——已修复

- **只在初始化探测一次**：`YdotoolBackend.__init__` 末尾
  `self.escapes_supported = _ydotool_escapes(self._run)`
  （`autopaste.py:728-732`），`type_text()` 只读字段（`:777-793`），不会每次
  输入 spawn 进程。`test_probe_runs_once_at_init` 用同一个 runner 建两个实例、
  各输入两次，断言 `type --help` 调用数 = 2（每实例一次），能抓住“每次注入都
  探测”。
- **探测方法**：`_ydotool_escapes()` 调 `ydotool type --help`
  （`capture_stdout=True`），`returncode != 0`、抛异常、stdout 为空一律
  `False`（`:675-693`）。判定只看 stdout 是否含 `--escape` / `-e,`。
- **失败安全默认成立**：探测 False 时**不传 `-e`**，并对含 `\` 或 C0/DEL 的
  文本在调用 `_exec` **之前** `raise Abort`（`:777-785`）；测试
  `test_old_ydotool_rejects_backslash_text/control_chars` 断言
  `runner.calls == []`（拒绝发生在任何 ydotool 进程之前），
  `test_probe_failure_is_treated_as_unsupported` 断言 rc≠0 → False。工具缺失
  时在更早的 `which()` 就 `BackendUnavailable`，不会走到探测。
- **最关键的发行版兼容性成立（上游源码核对）**：Ubuntu 22.04/24.04、Debian 12
  的 **v0.1.8** `Tools/Type/Type.cpp::ShowHelp()` 打印到 **stderr**，且没有
  `-e`；本实现只读 stdout → 判“不支持”，正确（虽然原因是“没读到 help”而非
  “看到没有 -e”）。**v1.0.3** 的 `Client/tool_type.c` 根本没有
  escape/`-e`，`show_help()` 里也没有 `--escape` → False。v1.0.4+ 帮助含
  `-e, --escape` → True。因此不存在“探测 False 却仍会被上游二次解码”的漏洞。
- **`--list-backends` 暴露结论**：`format_backends()` 在 socket 可用时调用同一
  `_ydotool_escapes(runner)`，输出“支持 -e（关闭转义）”或“不支持 -e（旧版
  < 1.0.4：含反斜杠的文本会被拒绝；建议升级或改用 wtype）”
  （`:1488-1497`）。`test_list_backends_reports_escape_support` 对两种 help
  各断言关键子串；`capabilities()["escapes_supported"]` 也对外暴露
  （`:812-817`，其余后端为 `True`/`None`）。单一探测函数被两处复用，
  诊断与真实调用不会漂移。
- **Minor m3（过度收紧 + 文案不准）**：旧版（v0.1.3–1.0.3 及 0.1.8）**没有
  escape 功能**，`\` 在 `ascii2keycode_map`/`Table_*Keys` 里是普通可打印键，
  本可安全地字面输入。当前实现对旧版连 `\` 一起拒绝，错误信息还写“旧版会转义
  或把 -e 的参数当文本”——对“反斜杠”这一项不成立。影响面是 Ubuntu 24.04/
  Debian 12（apt 装到的 0.1.8）用户无法输入 Windows 路径、正则、LaTeX 等；
  这是相对 02.1 之前可用状态的可用性回归（不是安全回归）。**注意**：控制字符
  的拒绝是必要的——v0.1.8 `TypeText()` 对不在表里的字符直接 `return -pos`
  停止、v1.0.3 `type_char()` 对 `-1` 直接 `return`，都会**静默丢字/截断**，
  所以“旧版拒绝 C0/DEL”必须保留。建议：旧版只拒绝 C0/DEL（及任何需要转义的
  字符），反斜杠放行；或至少修正文案。当前实现符合本批次验收口径
  （“含反斜杠/控制字符应被拒绝而不是静默打错”），故仅记 Minor。
- **Nit n1**：`_run()` 本身没有 `timeout`，探测是新的调用点，wrap 脚本类
  ydotool 若卡住会让后端初始化挂死（注入本来也会挂，属既有问题）；“探测失败
  安全默认”只覆盖异常/非 0 退出，不覆盖挂起。

## 架构影响说明

- 入口契约收敛为单一函数 `console_main(argv) -> int`：脚本、`-m`、pip/pipx
  console script 三条路径同源，信号安装成为**进程入口职责**而非 `main()` 职责；
  `main()` 保持可被库/测试直接调用的纯净语义。
- 外部工具契约从“固定 argv”升级为“按能力探测的 argv”：`YdotoolBackend`
  增加 `escapes_supported` 能力位，`capabilities()` 与 `--list-backends` 复用
  同一探测函数，形成“探测→能力位→argv/诊断”的单一事实来源；后续新增外部
  工具应沿用“探测一次并 fail-closed”的模式。
- REPL 粘贴缓冲的契约从“读到上限附近就停”改为“截断 + 排空到终止序列 +
  显式提示”，`LineEditor._read_paste()` 成为“输入长度上限（SECURITY #10）”
  的唯一执行点（字节口径，与 `MAX_PAYLOAD` 的字符口径分离）。
- 测试基础设施新增跨假后端的共享 `EventLog`，使 remap/restore 与按键的**相对
  顺序**首次可断言；这是后续验证任何“临时改键—注入—还原”流程的基础设施，
  不增加生产复杂度。
