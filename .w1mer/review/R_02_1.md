## Conclusion

B1 的修复方向与实现都正确：`ydotool type` 现在显式带 `-e 0`，且放在 `--` 之前；
上游 v1.0.4 的 `-e/--escape=BOOL` 是必选参数，命令行为文本默认 `enable_escape=1`，
因此这是唯一能关闭转义的位置。关闭后 `\n`/`\t`/`\xNN`/末尾 `\` 都只作为字面字符
走 `ascii2keycode_map`，不再触发上游 `escape()`，`validate_payload` 与 Wayland
“多行必确认”两道闸门重新生效，也没有“反斜杠被吞”的新回归。M1（wtype 修饰键映射到
`logo`、发送前 Abort）与 M2（GNOME 下 ydotool 优先、无 socket 回落 wtype、协议失败
只报错不重试）也都按预期落地，测试对 argv/调用次数做了真断言。

但修复引入了一个未处理的版本边界：`-e` 是 ydotool **v1.0.4 才加入**的选项；
v1.0.0–v1.0.3 的 `getopt_long` 会把 `-e` 报为未知选项后把 `0` 当成待输入文本
（静默多敲一个 `0`），v0.1.8（Ubuntu 22.04/24.04/25.x、Debian 12 的仓库版本）
直接以退出码 2 失败。这会让本工具在 GNOME 的主要目标发行版上完全不可用，属于本次
修复引入的功能性回归，故结论为 **issues**（安全修复本身无需回退）。

## 逐项结论

### 1. B1：已堵死（ydotool 字面量输入）

- **argv 证据**：`autopaste.py:748`
  `self._exec(["type", *self._delay_args(), "-e", "0", "--", chunk])`。
  `_delay_args()` 在 delay>0 时给 `--key-delay <ms>`（`:704-706`），`--` 永远在文本前。
- **上游语义**：ydotool v1.0.4 `tool_type.c` 中 `{"escape", required_argument, 0, 'e'}`
  且 `optstring "hd:D:H:f:e:"`；无 `-f` 时 `enable_escape = 1`。`-e 0` 是
  `strtol(optarg)=0`，正是关闭转义；`-e` 在 `--` 之前，不会被当作文本。上游帮助文本
  也写明 “Escape is enabled by default when typing command line arguments”。结论成立。
- **四类输入均为字面量**：`-e 0` 后主循环 `enable_escape ? escape(...) : pstr[i]`
  直接取字符，`escape()` 完全不执行。因此 `\n`、`\t`、`\x1b`、末尾单独 `\`
  分别按 `KEY_BACKSLASH`/`n` 等字符逐个 `type_char`，不会再生成换行/ESC；
  末尾 `\` 也不再进入上游 `escape()` 的越界读路径。`ascii2keycode_map['\\'] =
  KEY_BACKSLASH`，反斜杠不会被吞。
- **两道闸门重新生效**：
  - 控制字符：`main()` 在构造 Typer 之前对所有 `args.key` 调
    `validate_payload`（`:1486-1487`），真实 ESC/NUL 仍被拒；字面 `\x1b` 只是
    4 个可打印字符，ydotool 侧不再“解码复活”为 ESC。
  - 多行确认：`multiline_risk()`（`:909-922`）只对**真实换行**返回风险；ydotool
    `can_focus_info=False`，所以含真实 `\n` 的输入在 CLI 下必走 `_confirm`
    （`:1517-1524`），非 tty 直接退 3。字面 `\n` 不含真实换行，ydotool 现在也不会
    生成换行，两边语义一致，不再存在“确认看不到、工具却换行”的绕过。
  - REPL 路径同样先 `validate_payload`（`:1213/:1221/:1241`）；其多行只警告是
    R_02 已记录的既有语义，与本修复无关。
- **测试守护**：`tests/test_backends.py:286` 断言完整 argv
  `["ydotool","type","--key-delay","8","-e","0","--","hello"]`，并额外断言
  `-e` 位于 `--` 之前（`:292-294`）；把 `-e 0` 删掉或挪到 `--` 之后都会红。
  `:296` 用字面反斜杠串（含 `\n`/`\x1b`/`\t`/末尾 `\\`）断言 `argv[-1] == text`
  且没有任何 C0/DEL 字符，覆盖了“不吞反斜杠、不产生控制字符”的 Python 侧契约。
- **残余**：FakeRunner 只能证明“传了 `-e 0`”，无法证明外部 ydotool 的版本是否
  接受它；这正是下面 Major N1 的来源。

### 2. M1：已修复（wtype `super` 修饰键）

- `WTYPE_MODIFIERS`（`autopaste.py:170-174`）把 `super/win/meta → logo`，
  `ctrl/control → ctrl`，`alt/shift` 同名。上游 wtype `main.c` 的 `mod_names[]`
  确有 `logo`/`win`，没有 `super`；`-M super` 会
  `fail("Invalid modifier name 'super'")`。映射方向正确。
- `WtypeBackend.press()`（`:592-611`）先构造 `wmods`：`WTYPE_MODIFIERS.get(mod)`
  为 `None` 时在拼 argv/调 `_exec` **之前** `raise Abort`；`_exec` 是唯一执行点，
  所以未知修饰键零调用 runner。测试 `test_unsupported_modifier_aborts_before_running`
  断言 `runner.calls == []`；`test_unknown_modifier_aborts` 保留 Abort 语义。
  `parse_combo` 本身也会先拒绝非 `MODIFIERS` token，`hyper+t` 实际在解析阶段就
  Abort；防御性 `None` 分支当前不可达（所有 `MODIFIERS` 键都有映射），无害。
- `-M`/`-m` 严格成对：先全部 `-M`、再 `-k`、再 `reversed(wmods)` 的 `-m`
  （`:605-611`），同一 argv 一次交给 wtype。异常路径上：参数非法会在 wtype
  `parse_args` 阶段、创建虚拟键盘之前失败；进程中途死亡时合成器在 client 销毁时
  清空键盘状态，因此没有“按下未释放”的 Python 侧窗口。若 `-k` 的 keysym 非法，
  上游同样在 parse 阶段 fail。测试 `test_super_modifier_mapped_to_logo`
  断言完整 argv（`-M logo ... -m logo`），`test_meta_and_win_aliases_mapped_to_logo`
  再覆盖两个别名（用切片断言 `-M logo` / `-m logo`，配合前者的全量断言足够）。

### 3. M2：已修复（GNOME 选择顺序 + 不静默重试）

## Findings

### Major

- **N1 `-e 0` 无版本/能力门槛：ydotool < v1.0.4 会失败或静默多敲 `0`（本修复引入）**
  - 证据（上游源码）：
    - v1.0.4 `Client/tool_type.c` 才出现 `-e, --escape=BOOL`；
    - v1.0.0–v1.0.3 没有 `-e`，且 `getopt_long` 的 `?` 分支只打印错误后继续，
      `0` 变成位置参数：`ydotool type --key-delay 8 -e 0 -- hello` 会先输入
      字面 `0` 再输入 `hello`（**静默错误输入**）；
    - v0.1.8（`Tools/Type/Type.cpp`，boost program_options）遇到未知 `-e`
      抛异常，`Exec` 捕获后返回 2（**该后端完全不可用**）。
    - 发行版现状（Repology）：Ubuntu 22.04/24.04/25.04/25.10、Debian 12 均为
      0.1.8；Ubuntu 26.04、Debian 13、Fedora 39+、Arch 为 1.0.4。README 的
      `apt install ydotool` 正好覆盖前一组，且 GNOME 是 ydotool 的主场。
  - 影响：不是安全回退（B1 在 >=1.0.4 上仍正确），而是兼容性回归；旧版根本没有
    转义功能，本来不需要 `-e 0`。此外错误信息会把用户引向 `ydotoold`
    （`YdotoolBackend._exec` 的通用 hint），与真实原因不符。
  - 建议：在 `YdotoolBackend` 初始化时做能力探测（如 `ydotool type --help`
    输出是否含 `-e, --escape`，或解析 `ydotool --version` >= 1.0.4），
    探测结果决定 argv 是否带 `-e 0`；旧版不带（其本就没有转义），探测失败时给
    “升级 ydotool 或改用 wtype”的明确错误。测试接缝需要可注入探测结果，
    并补“旧版 argv 不含 `-e`”与“新版含 `-e 0`”两条 argv 断言。

### Nit

- `test_meta_and_win_aliases_mapped_to_logo` 只断言 `-M`/`-m` 切片，未断言 `-k a`；
  已有 `test_super_modifier_mapped_to_logo` 的全量 argv 兜底，属于可接受强度。
- `WTYPE_MODIFIERS.get()` 的 `None` 分支当前不可达（`parse_combo` 已保证 token 属于
  `MODIFIERS`，而 `MODIFIERS` 与 `WTYPE_MODIFIERS` 的键集完全一致）；保留为
  防御性检查可以，但不要误以为它承担了“未知修饰键拒绝”的职责（实际由
  `parse_combo` 负责）。

## 架构影响说明

- 外部进程边界新增了一条**版本化契约**：`-e 0` 只对 ydotool >=1.0.4 有效，后端
  必须在调用前做能力探测；否则“固定 argv”不再是跨版本的稳定契约。
- `WTYPE_MODIFIERS` 成为独立于共享 `MODIFIERS`（X11 keysym 名）的映射层：
  共享层继续表达用户词汇（`super/win/meta`），后端各自翻译，后续新增后端应沿用
  这个模式，而不是改共享别名表。
- 后端选择从“按会话类型固定顺序”扩展为“会话类型 × 桌面环境”的纯函数；
  `--list-backends` 已复用同一函数，保持单一事实来源。运行期不做跨后端回退，
  避免部分输入后的重复注入。
- 安全闸门的职责边界进一步明确：`validate_payload`/`multiline_risk` 只保证
  “交给后端的字符串语义”，后端必须保证“工具不会二次解码”。`-e 0` 属于后者，
  以后新增外部工具时必须逐一确认其是否有隐式转义。
