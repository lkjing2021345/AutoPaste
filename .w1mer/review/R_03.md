## Conclusion

三条提交的方向与主路径实现是正确的：`--window` 的枚举→匹配→歧义处理→激活→轮询焦点→
倒计时后再复核→焦点丢失退出 3 是一条完整的 fail-closed 链，代码里**没有任何**"激活/校验失败
就退回当前焦点继续敲"的分支（这是本批次最需要守住的东西，成立，证据见 §2）；`--paste-mode`
的备份 fail-closed、`finally` 恢复、`--dry-run` 零剪贴板调用、`validate_payload` 仍然前置也都
成立；批量提速改变了 flush/等待位置但没有改变 press/release 的顺序与成对关系，Unicode 的
remap 前 `XFlush`/`XSync` 也保留了。

但发现三类问题：

1. **REPL 的 `:w` 定向缺少倒计时后的焦点复核**（`repl()` 只做 `activate() and countdown()`
   就 `type_text`），而这正是 SECURITY.md #14 明文承诺"倒计时结束再复核一次，焦点离开立即
   取消"的场景 —— CLI 有、REPL 没有，属于本任务引入的功能与安全承诺不一致。
2. **枚举/激活前的只读属性读取没有套 `_x_trap`**：Xlib 的 BadWindow 是异步错误，
   `try/except` 抓不到，默认错误处理器直接 `exit(1)`；`_NET_CLIENT_LIST` 里出现刚关闭的
   stale xid 时 `--list-windows` 会"X Error"猝死而不是跳过该窗口。代码自己在
   `autopaste.py:788-789` 的注释就承认了这个机制，却只在两个写操作（XSendEvent /
   XSetInputFocus）外用了 `_x_trap`。
3. **`test_ambiguous_non_tty_exits_2` 依赖环境 `sys.stdin.isatty()`**：`main()` 用
   `tty=sys.stdin.isatty()` 决定 `pick_window` 是否进入交互选择，而该用例没有打桩；
   在真终端里直接跑 unittest 会停在 `readline()` 上挂住（CI/agent 的 stdin 是 /dev/null
   所以恰好绿）。属于测试可重复性问题，不是产品缺陷。

结论：**issues**（建议一个很小的修复子批次：REPL 复核、`_x_trap` 覆盖读路径、测试打桩
`isatty`；其余为 Nit/文档微调）。

## 逐项结论

### 1. 窗口定向的正确性

- **`_NET_CLIENT_LIST` 解析**：`_prop()`（`autopaste.py:416-443`）用一个统一出口读 32 位数组
  与 8 位字节串，`XGetWindowProperty` 的 `long_length = max(1, max_bytes//4)` 是 32 位单元，
  `format==32` 时按 `P(c_ulong)` 逐项取值 —— LP64 上每个 32 位值占一个 `long`，
  这个读法正确。`status != 0 or not data` 才判缺失，返回码语义（0=Success）正确。
  `nitems==0` 的两种情形：属性存在但为空 → 返回 `[]` / `b""`，`_prop32` 得 `[]`，
  `list_windows_x11` 视同"没有 EWMH 列表"转 `XQueryTree` 兜底（`:589-593`），行为合理。
  **残留（Nit N3）**：`_prop` 不看 `actual_type`/`actual_format`，只要 `data` 非 NULL 就当
  "属性存在"。Xlib 对不存在的属性通常返回 `prop==NULL`（`tests/support.py:211-218` 的假实现
  也按这个假设写），所以大概率没问题；但这层假设**未在真实 X 服务器上验证**，
  若某实现返回"非 NULL + format 0"，`_prop_text` 会返回 `b""`，`_window_info_raw:503-507`
  就会认为 `_NET_WM_NAME` 存在且为空，**不再回落 `WM_NAME`**，只设 WM_NAME 的老程序
  `title:` 匹配会失效。一行防御（`actual_type.value == 0 or actual_format.value == 0 → None`）
  即可消除该假设。
- **`_NET_WM_NAME` 非 UTF-8 降级**：`_window_info_raw:505` 用 `decode("utf-8","replace")`，
  不会抛；`WM_NAME` 走 `_decode_title()`（`:463-468`）先严格 UTF-8 再 latin-1，正确。
  `_fetch_name` 的 `finally` 只在 `name` 非空时 `XFree`（`:471-479`），没有 double-free；
  `_class_hint` 用 `POINTER(c_char)` 保留原始指针再统一释放（`:126-131`, `:482-496`），
  注释里点出的 `c_char_p` 自动转换陷阱是真的，写法正确。
- **`XQueryTree` 兜底的重复问题**：`_walk_clients`（`:566-580`）对每个非 override_redirect
  子窗口先判断 map_state==2 再收集，并**无条件递归**；重父化 WM 下 root→frame（无 WM_CLASS）
  →client，因此 frame 不会被收录、client 被收录一次，
  `test_query_tree_finds_client_inside_frame`（`test_window.py:62-68`）恰好覆盖这个形态。
  同一个 xid 不会被重复访问。**残留（Nit N2）**：兜底路径 (a) 不应用 `_skip_window_type`
  （`:597` 只作用于 EWMH 列表），(b) 若被嵌入的子窗口自己带 WM_CLASS（XEmbed/Java 等），
  父子会同时入选 —— 只会让 `pick_window` 多问一次，不会选错；无 EWMH 的会话才触发。
- **多匹配**：`pick_window`（`:744-785`）对 0 匹配与非交互多匹配都抛
  `WindowUnavailable(code=2)`，错误信息带候选 xid；交互终端才提示选择，回车=最上层（列表末尾），
  `q`/EOF=退出 3。**没有任何"取第一个"的分支**：唯一的"自动选"是"激活窗口命中候选之一"，
  并且会先往 stderr 说明（`:754-759`），随后激活+焦点校验兜底。
  `test_ambiguous_non_tty_exits_2_with_candidates`（`:208-215`）断言了退出码 2 且两个候选
  xid 都在消息里；`test_ambiguous_tty_cancel_exits_3` 断言 3。**结论：退出码确实是 2，未悄悄选第一个。**
  另注（Nit N5）：`list_windows_x11` 在没有 `_NET_CLIENT_LIST_STACKING` 时所有排序 key 退化为
  -1（`:602`），顺序变成 `_NET_CLIENT_LIST` 顺序，但提示语仍写"最上层在前"。

### 2. 激活与焦点复核（最危险的回归）

- **ClientMessage 字段**：`_client_message`（`:811-823`）`type=33`、`send_event=1`、
  `format=32`、`data.l[0]=2`（source indication = pager/tool，与 wmctrl 同款，可绕过部分
  焦点抢占策略）、`data.l[1..4]=0`；发送目标是 root 且事件掩码
  `SUBSTRUCT_MASK = SubstructureNotify|SubstructureRedirect`（`:84`, `:878`），符合 EWMH。
  测试 `test_sends_net_active_window_client_message`（`:255-265`）断言了 window/type/format/
  l[0]/mask。**Nit**：`data.l[1]`（timestamp）传 0=CurrentTime，部分 WM 对 CurrentTime 的
  activation 会拒绝，目前靠后面的 XSetInputFocus 兜底；读一次真实时间戳会更稳，不阻塞。
- **轮询超时上限**：`WINDOW_ACTIVATE_TIMEOUT=1.5s` + 兜底 `min(0.3, timeout)`，
  最坏约 1.8s 后失败（`:78`, `:859-897`），有界。
- **`XGetInputFocus` 的 None/PointerRoot**：`_focus_raw` 把 0/1 都映射为 `None`
  （`:606-615`），`_is_focused`/`_wait_focus`/`_is_focused` 的 parent 链上行都在 focus 为
  None 时直接 False（`:826-849`）。**行为是 fail-closed**：pointer-focus 的 WM 若一直返回
  PointerRoot，激活会以"无法把焦点切换到…"退出 2 而不是继续敲 —— 安全，但会误报，
  文档未提，属 Nit。
- **失败是否退化成"往当前焦点盲打"：否。** 证据链（全部是"抛/返回码"而非"继续"）：
  - `resolve_window`（`:2379-2390`）：后端无 `window_control` → 抛 `WindowUnavailable`；
    无匹配/歧义 → `pick_window` 抛（code 2）。
  - `activate_window_x11`（`:859-897`）：窗口已关 → 抛；XID 复用 → 抛；WM 拒绝且
    `XSetInputFocus` 后仍未拿到焦点 → 抛（带焦点抢占防护提示）。
  - `main`（`:2765-2783`）：`if not typer.activate_window(target): raise`；
    倒计时后 `if target is not None and not typer.is_window_focused(target.xid): return 3`；
    三者任一失败都在注入循环（`:2794-2801`）与 `send_text`（`:2791`）**之前**返回。
  - `Backend.is_window_focused` 默认返回 False（`:972-974`），即"不确定就当没焦点"，
    所以未来新增的、`window_control=True` 但没实现复核的后端也会 fail-closed。
  - `test_focus_lost_during_countdown_cancels`（`:424-429`）断言退出 3 且
    `type_text.assert_not_called()`；`test_activate_false_exits_2` 断言退出 2 且未注入。
  - 残余 TOCTOU（复核通过→第一条 XTest 事件之间被抢焦点）理论存在，但那是不可消除的竞态，
    不是本批次引入的回退。
- **REPL `:w` 的洞（Major M1）**：见 Findings。`activate()` 成功后 `countdown()` 结束就直接
  `type_text`/`press`（`:2318-2321`, `:2329-2330`, `:2335-2336`, `:2353-2356`），
  没有 CLI 的 `is_window_focused` 复核。REPL 里用户在倒计时内点走焦点，文本会进**当前**
  窗口 —— 正是 SECURITY.md #14 承诺要拦的情形。

### 3. `--paste-mode` 的剪贴板安全

- **备份失败 fail-closed**：`paste_text:1798-1814`，非文本 targets / `read()` 抛
  `ClipboardError` / 备份 >4 MiB 都抛 `ClipboardUnsafe(code=2)`；
  `send_text` 只捕获 `ClipboardError`（`:1855`），`ClipboardUnsafe` 直穿到 `main` 的
  `except Abort → return e.code`（`:2812-2814`），**不会**降级成打字。
- **恢复覆盖所有异常路径**：`try: write→settle→press→wait  finally: write(backup)`
  （`:1817-1827`）。Ctrl-C（`_install_signals` 把 SIGINT/SIGTERM 转成 KeyboardInterrupt）
  → `finally` 恢复；目标窗口消失/`press` 抛 `BackendError` → `finally` 恢复；
  `clip.write(data)` 自己失败 → 仍恢复（幂等无害）。恢复失败只 stderr 警告不抛
  （`:1824-1827`），不会再制造二次异常。测试 `test_restore_runs_when_press_fails`
  （`test_paste.py:199-205`）断言写入序列是 `[b"new", b"old"]`。
  **Nit（N4）**：`KeyboardInterrupt` 中断在 `clip.write`/恢复子进程（超时 2s）期间没有单独测试。
- **`--dry-run` 零剪贴板调用**：dry-run 分支（`:2713-2752`）只读 `focus_info()`，
  不构造 clipboard、不调 `send_text`；`test_dry_run_never_touches_clipboard`
  （`test_paste.py:313-322`）断言 `make_clipboard` 未被调用、`paste_text` 未被调用、
  `press`/`type_text` 未调用。成立。
- **`validate_payload` 仍然前置**：`:2693-2694` 在构造 Typer 与任何注入/剪贴板动作之前
  对每个 payload 校验；paste-mode 走的是同一个 `joined`（`:2691`），ESC 等控制字符仍然被拒。
- **敏感内容进全局剪贴板的风险已写清**：SECURITY.md #10（`SECURITY.md:84`）明确
  "payload 会进入全局剪贴板，同会话任何程序/剪贴板管理器都能读取并留存历史；恢复原内容不等于
  擦除"，README 的已知限制也重复了一遍，`--no-clipboard-backup` 还会在 stderr 二次警告
  （`:2787-2790`）。这一点达标。
  **Nit（N6）**：`MAX_CLIP_BACKUP` 的检查在 `clip.read()` **之后**，读取本身没有字节上限
  （只有 1s 超时），本地 selection owner 理论上可以在 1s 内灌入大量数据；
  另外 xsel 不支持列 targets，`is_text_targets(None)=True`，所以"非文本拒绝覆盖"对 xsel
  不成立，文档里的"仅文本"承诺对 xsel 略强于实现。

### 4. 提速等价性

- **`--delay 0` 与逐字符模式的事件序列**：`type_text:1074-1109` 与
  `_type_text_per_char→type_char→_tap` 产生的都是 `[shift↓,] key↓ key↑ [,shift↑]`，
  `\n`/`\t` 走 `_press_raw` 与 `press` 同一套 `_tap_raw`/`_tap`，`\r` 两种模式都跳过。
  `test_event_sequence_identical_to_per_char`（`test_speed.py:48-56`）用同一文本
  `"aAbB\n\t"` 逐事件比对两次 `xtst.events`，是全量断言而不是"没抛异常"。
  修饰键配对：`_tap_raw:1116-1126` 与 `_press_raw:1157-1169` 都在 `finally` 里释放 shift/
  修饰键；`test_shift_released_when_batch_tap_raises` 断言异常后最后一条事件是 `(50, False)`。
- **flush 分块**：`budget = max(1, 250//delay_ms)` 或 256（`:1082-1084`），
  `test_zero_delay_flushes_every_256_chars` / `test_chunk_size_bounded_by_250ms_budget`
  分别断言 4 次 flush（256/512/768+收尾、31/62/93+收尾），与源码推导一致。
- **XTest 服务端 delay 的单位与溢出**：`_delay_ms`（`:1269-1273`）先 `min(delay, 5.0)`
  再 `round*1000`，最大 5000ms，`c_ulong` 不会溢出；<1ms 抬到 1ms 有测试
  （`test_sub_millisecond_delay_has_1ms_floor`）。delay 只加在 key press 上，
  `test_delay_is_put_on_press_event` 断言 `delays == [10, 0]`，语义确实是"相邻字符间隔"
  （服务端在处理 press 前等待），与旧版"tap 完 sleep(delay)"的间隔等价。
- **Unicode 的 remap 前 XSync 未丢**：`type_text:1099-1103` 在走慢路径前显式
  `XFlush` 并把 `n` 归零，`_remap` 内部仍然 `XSync`（`:1054-1064`）；
  `test_unicode_uses_slow_path_and_restores_keymap` 断言 `tap,tap,remap,tap,tap,restore`
  的完整顺序，`test_unicode_flushes_pending_events_first` 断言 remap 发生在已排队事件之后。
  这是本批次最容易被"为了快"破坏的地方，代码没有破坏它。
- **`--safe` 回退是否真逐字符**：`--safe` 置 `backend.batch_enabled=False`（`:2697-2698`），
  `type_text` 立刻 `return self._type_text_per_char(text)`（`:1080-1081`）；
  `test_use_xtest_delay_false_falls_back_to_per_char` 断言 flush 数=2（每字符一次）。
  **Nit（N7）**：`test_safe_flag_disables_batch` 断言的是被 mock 的 Typer 上的赋值，
  只证明"main 设置了标志"，不证明真实后端路径；真实路径由 `USE_XTEST_DELAY=False`
  那条用例覆盖，强度可接受但别把它当成端到端证据。
- **性能回归风险（Minor M3）**：`--delay` 允许到 5s，而批量模式把等待放在 XTest 服务端。
  源码注释（`:289-291`）自己承认"某些 Xorg/驱动把 XTest 的 delay 实现成服务器睡眠
  （会卡整机输入）"，但**没有自动阈值**，只有一个要改源码的模块常量 `USE_XTEST_DELAY`。
  旧版是客户端 `sleep`，服务端不会长时间停摆。具体服务端实现**未验证**；
  建议 `delay_ms > QUEUE_BUDGET_MS`（>250ms）时自动走 `_type_text_per_char`，既保住旧语义
  又不需要用户改源码（该区间本来 flush 数已是每字符 1 次，没有性能收益）。

### 6. 过程风险：验证时误触发真实输入（hi 进了 Alacritty）

- 判断：这是**验证流程**问题，不是测试套件问题 —— `tests/` 里的用例全部走
  `mock.patch.object(autopaste, "Typer")` / 假 `x11`/`xtst` / `FakeRunner`
  （`test_window.py:20-29, 329-349`；`test_paste.py:228-246`），`tools/bench.py`
  也在构造后端前替换了模块全局（`tools/bench.py:42-51`），不会触碰真实 X。
  误触发应来自人工实跑（`--dry-run` 之外的验证）。
- 但确实暴露一个设计缺口：**除 `--dry-run` 外没有"强制沙箱/禁注入"开关**。
  任何一次忘带 `--dry-run` 的冒烟验证都会立刻变成真注入（本程序的设计如此），
  agent/CI 里尤其危险。建议登记为后续任务（不要在本批次改）：例如
  `AUTOPASTE_NO_INJECT=1` 或 `--no-inject`，在后端 `type_text/press` 入口直接抛错，
  并在 `tests/` 里默认设置，使"忘记打桩"最多报错而不是误敲。

## Findings

### Major

- **M1 REPL 的 `:w` 定向在倒计时后不复核焦点（本任务引入，与 SECURITY.md #14 冲突）**
  - 证据：`repl()` 的 `activate()`（`autopaste.py:2247-2259`）只负责解析+激活；
    四条提交路径都是 `if activate() and countdown(cfg.sleep, typer): typer.type_text(...)` /
    `typer.press(...)`（`:2320-2321`, `:2329-2330`, `:2335-2336`, `:2353-2356`），
    中间**没有** CLI 里的 `typer.is_window_focused(target.xid)` 复核（对比 `:2779-2783`）。
    `SECURITY.md:64` 写的是"倒计时结束再复核一次，焦点离开立即取消（退出 3）"，未限定 CLI；
    README 的 REPL 表格也把 `:w` 作为正式功能列出（`README.md` 的 REPL 段）。
  - 影响：REPL 用户在 2s 倒计时内点走焦点 → 文本/组合键进入当前窗口，正是本批次要防的
    "敲错窗口"事故；CLI 路径不受影响。
  - 影响面/触发：需要同时使用 `:w` + 倒计时 + 期间鼠标点走焦点；不是默认路径，但属于
    安全承诺的功能洞。
  - 建议：`activate()` 返回目标 xid（或把复核封装成 `focus_ok(target)`），在
    `countdown()` 返回 True 之后再判一次，失败就打印"焦点已离开"并跳过本次注入
    （不退出 REPL）；同时补一条 REPL 用例（`focus_script` 模拟倒计时期间焦点漂移）。

### Minor

- **M2 枚举/激活前的只读属性读取未套 `_x_trap`：stale xid 会让进程"X Error"猝死**
  - 证据：`autopaste.py:788-789` 的注释自己写明"Xlib 默认错误处理器会 exit(1)"，
    但 `_x_trap` 只包了 `XSendEvent`/`XRaiseWindow`/`XSetInputFocus`（`:877-888`）。
    `_attrs`/`_prop`/`_class_hint`/`_fetch_name` 的 `try/except` 只能接住 Python 异常；
    `XGetWindowAttributes`/`XGetWindowProperty` 的 BadWindow 是在 `_XReply` 里同步触发
    Xlib 错误处理器的，默认实现直接 `exit(1)`。
    触发点：`list_windows_x11:596-601`、`_window_info_raw`（`activate_window_x11:863` 的
    XID 复用检查）、`focused_xid` 的 parent 链读取。
  - 影响：`--list-windows` 是只读诊断命令，在"枚举瞬间有窗口关闭"时会以
    `X Error of failed request: BadWindow` 退出（退出码 1，而不是跳过该窗口），
    会误导用户以为是本程序 bug；`--window` 的竞态同理。
  - 建议：把"枚举/校验读"也放进 `_x_trap`（注意它是全局 handler，避免嵌套；可在
    `list_windows_x11` 外层包一次、`activate_window_x11` 的预检处包一次）。
    补测试可以用 FakeX11 增加"指定 xid 抛 X 错误"的开关（当前假后端不会产生 X 错误，
    所以这类问题测试永远看不到）。
- **M3 `--delay > 250ms` 时把等待放到 XTest 服务端，可能冻结整个 X 会话**
  - 证据：`type_text:1080-1089`（批量路径把 `delay_ms` 传给 `XTestFakeKeyEvent` 的 press）
    + 源码注释 `:289-291` 自己承认"某些 Xorg/驱动把 XTest 的 delay 实现成服务器睡眠
    （会卡整机输入）"；`--delay` 上限 5s（`MAX_DELAY`），而自动回退**不存在**，
    只能改模块常量 `USE_XTEST_DELAY` 或加 `--safe`。
  - 影响：旧版是客户端 sleep，服务端不会停摆；新版在 `--delay 1..5` 且用户忘记 `--safe`
    时可能让整个桌面卡住数秒（每个字符一次）。具体服务端行为**未验证**。
  - 建议：`delay_ms > QUEUE_BUDGET_MS` 时自动走 `_type_text_per_char`
    （该区间每字符本来就要 flush 一次，没有吞吐收益），或把 `USE_XTEST_DELAY`
    暴露成 CLI/env 开关并在 README 写明适用 delay 区间。
- **T1 `test_ambiguous_non_tty_exits_2` 依赖环境 `isatty()`，真终端下会挂住**
  - 证据：`test_window.py:404-409` 未打桩 `sys.stdin`；`main` 用
    `tty=sys.stdin.isatty()`（`autopaste.py:2706-2707`），tty 为真时 `pick_window:767-785`
    会 `readline()` 等待输入。交互式跑 `python3 -m unittest` 会阻塞（或读入 `q` 后变 3 失败）。
  - 建议：在该用例（以及 `MainWindowTests._run`）里
    `mock.patch("sys.stdin.isatty", return_value=False)`；长期看可让 `main` 接受注入的
    `tty` 判定，测试不必依赖环境。

### Nit

- **N1 `--paste-key` 只校验修饰键名，不校验后端能否解析该键**：`main:2684-2688` 只做
  `is_combo` + `parse_combo`；真正的按键解析发生在 `paste_text` 的 `typer.press` 里
  （X11 `_resolve_key` / ydotool `_keycode`）。失败时剪贴板已被写过一次（虽然会恢复）才报错。
  可在倒计时前用后端做一次"只解析不发送"的预检。
- **N2 `_walk_clients` 兜底不应用 `_skip_window_type`，且被嵌入的子窗口若自带 WM_CLASS
  会父子同时入选**（仅无 EWMH 会话；后果是多个候选项，不是选错）。
- **N3 `_prop` 未按 `actual_type`/`actual_format==0` 判缺失**（见 §1；取决于真实 Xlib 是否
  返回非 NULL 空指针，未验证）。建议一行防御。
- **N4 `paste_text` 的 KeyboardInterrupt 路径无测试**（结构上 `finally` 已覆盖）。
- **N5 无 `_NET_CLIENT_LIST_STACKING` 时排序退化**，但 UI 仍宣称"最上层在前"。
- **N6 `MAX_CLIP_BACKUP` 在 `clip.read()` 之后才检查**（读取无字节上限，仅 1s 超时）；
  xsel 无 TARGETS 时 `is_text_targets(None)=True`，与文档"仅文本"略有出入。
- **N7 `activation` 的 `data.l[1]` timestamp 传 CurrentTime**，部分 WM 会拒绝，靠兜底；
  不阻塞。
- **N8 `--delay` 在批量模式有 1ms 下限**（`_delay_ms`），`--delay 0.0004` 的实际间隔是 1ms 而非
  0.4ms；CHANGELOG/README 已写明，属可接受语义差异。

## 遗留（建议登记为后续任务，本批次未改、未在此创建任务行）

1. **强制禁注入开关**（来自 §6 的过程事故）：`AUTOPASTE_NO_INJECT=1` / `--no-inject`，
   后端注入入口直接抛错；`tests/` 默认开启，杜绝"忘打桩就真输入"。优先级：中。
2. **`--window` 的 focus-follows-mouse / PointerRoot 场景**：目前一律 fail-closed 报错，
   可考虑用 `_NET_ACTIVE_WINDOW` 作为副判据（需证明不会误判）。优先级：低。
3. **`--list-windows` 的性能**：每个窗口约 7 次 X 往返，会话窗口多时偏慢；可缓存 atom、
   先读 `_NET_CLIENT_LIST` 再懒加载 class/title。优先级：低。
4. **xsel 路径的"仅文本"契约**：要么文档注明 xsel 无法判别 targets，要么检测读取结果的
   内容类型。优先级：低。

## 架构影响说明

- X11 窗口控制成为一个**跨后端能力位**（`capabilities()["window_control"]`），并且是
  **三态语义**：`list_windows`/`activate_window`/`focused_window_id`/`is_window_focused`
  四个新方法默认"不可用/不确定"，只有 X11 实现；`is_window_focused` 默认 False 使
  任何未来后端在未实现复核对时自动 fail-closed。这是本批次新增的、需要长期保持的契约。
- `--window` 引入"激活 → 倒计时 → 复核 → 注入"四段式，`main` 是唯一组装点；
  **REPL 复用了前两段却没复用第三段**（M1），说明该四段式应该被提取成一个可复用函数
  而不是靠两条路径各自记得。
- 剪贴板成为**新的外部进程边界**（`xclip`/`xsel`/`wl-copy`，固定 argv、`shell=False`、
  有超时），`Clipboard` 抽象与 `ClipboardError`/`ClipboardUnsafe` 的分层是
  "可降级错误 vs 必须停"的分界线：前者降级逐字符，后者退出 2。后续任何"默认不碰系统
  共享状态"的功能都必须遵守这两级错误分类。
- 批量注入把 `--delay` 的等待位置从客户端移到 XTest 服务端，`--safe`/
  `USE_XTEST_DELAY=False` 成为唯一回退；258ms 的队列预算替代了"每字符一次 flush"的
  旧契约，中断残留上限由 `QUEUE_BUDGET_MS` 定义。这是性能契约，也是新的事故面（M3）。
- `tests/support.py` 的假 X11 现在是"窗口/属性/焦点/ClientMessage"的完整替身，
  但它**不模拟 X 错误**且对缺失属性返回 NULL —— 这两点决定了它无法守护 M2/N3 类问题。
