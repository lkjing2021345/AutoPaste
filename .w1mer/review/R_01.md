## Conclusion

方向正确：没有为测试改动任何生产代码，测试通过替换既有的模块级
`autopaste.x11` / `autopaste.xtst` 获得可测性，不引入新抽象，单文件 CLI 的
复杂度没有被测试需求污染；62 个用例大多数是精确的行为断言，三条重点测试
（keymap 还原、`_tap` 异常时 Shift 释放、press 修饰键顺序）确实能捕获主要
回归。但打包入口引入了一处文档承诺的真实退步（安装后的命令绕过
SIGTERM/SIGHUP 处理），`>=3.8` 的兼容性声明没有 CI 背书，且 `dry-run`、
remap 时序、超限粘贴三处测试存在假绿或把错误契约固化的问题。结论为
**issues**，无阻塞级问题，建议以子任务方式修复后再进入下一批次。

## 逐项结论

### 1. 测试质量（62 用例）

- 计数属实：`test_cli` 7 + `test_core` 20 + `test_lineeditor` 17 +
  `test_typer` 18 = 62。
- **大部分是真行为断言**：`test_plain_char_taps_keycode`、
  `test_shifted_char_presses_shift`、`test_combo_modifier_order`（精确到
  按下/释放顺序）、`test_modifiers_released_when_tap_raises`、
  `test_bracketed_paste`（`\r\n`/`\r` 归一）、`test_backspace_after_paste_clears_paste`
  都断言了具体事件/返回值，删掉对应实现会失败。
- **三条重点测试的判定**：
  - `Unicode remap 后必须还原 keymap`（`test_typer.py:63`）：能捕获
    「忘记还原」「还原失败/未清 `_remapped`」；`test_unicode_restores_even_when_tap_fails`
    （`:78`）也能捕获异常路径漏还原。**但不能捕获时序错误**（见 M4）。
  - `_tap 抛异常时 Shift 仍释放`（`:95`）：真实有效；异常发生在 key press，
    断言最后事件是 `(50, False)`，去掉 `finally` 会失败。
  - `press 修饰键顺序`（`:108`）：真实有效；完整序列 `ctrl↓ alt↓ t↓ t↑
    alt↑ ctrl↑`，顺序或释放逻辑变化会失败。
- **假绿/弱断言**：`test_dry_run_exits_zero`（M3）、remap 时序（M4）、
  `test_resolvable`（m3）、`test_delay_attribute`（m4）、
  `assertIn("6", ...)`（m5）。`test_delay_attribute` 只验证构造函数存了参数，
  不是行为；`test_resolvable` 在 `spare_kc` 存在时恒返回 `[]`，即使实现永远
  返回 `[]` 也会通过。
- **括号粘贴/超上限截断**：`test_bracketed_paste` 验证了字节级归一，合格；
  `test_oversized_paste_truncated`（`test_lineeditor.py:82`）只验证了「恰好
  被读走 `limit+1` 字节并返回」，但把这个 off-by-one 固化成期望，且没有验证
  剩余字节的消费契约（M5）。它**部分**验证了字节消费，但验证方向是错的。

### 2. Python 3.8 兼容

- 静态扫描 `autopaste.py`：`list[str]`、`dict | None`、`str | None`、
  `tuple[...]` 全部只出现在注解中，文件顶部有
  `from __future__ import annotations`；没有 `str.removeprefix`、`match`、
  walrus、PEP 585 的运行时实例化。`tests/` 无 3.9+ 语法。**代码本身大概率
  兼容 3.8**。
- 但 `requires-python = ">=3.8"`、`Programming Language :: Python :: 3.8`
  classifier、README「Python ≥ 3.8」都没有 CI 背书：`check` 矩阵 3.9–3.13，
  `tests` 只 3.9/3.13，没有 3.8 job。见 M2。

### 3. 打包正确性

- **动态版本是单一来源**：`[tool.setuptools.dynamic] version = { attr =
  "autopaste.__version__" }`，`__version__` 是字面量，setuptools 可静态读取；
  代码库中没有第二个版本常量（CHANGELOG 是人工记录）。✅
- **入口可安装**：`[project.scripts] autopaste = "autopaste:main"` 生成
  wrapper 后 `sys.exit(main())`，退出码能透传；CI `package` job 用
  `pip install --no-deps .` + `autopaste --version` 覆盖了「能装、能跑」。
  但入口绕过信号处理，见 M1。
- **LICENSE 分发**：`license = { file = "LICENSE" }` 是 PEP 639 之前的表格式
  写法，setuptools ≥77 起已弃用（未来会移除）；当前仍可用且会随包分发。
  CI 没有断言 wheel 内确实含 LICENSE，也没有断言安装后的包元数据版本等于
  `__version__`（`autopaste --version` 读的是模块常量，二者可以漂移）。
  见 m2。
- **干净 venv 的 `pip install .`**：本次未能实际执行；按 pyproject 推导应
  成功（构建隔离会装 setuptools，`py-modules` 指向根目录 `autopaste.py`）。
  `pip install` 本身不 import 模块；但运行 `autopaste` 会 import 并加载
  `libX11`/`libXtst`，这是既有约束，README 已声明需要 X11 环境。

### 4. CI 正确性

- `tests` job 的 `env -u DISPLAY python -m unittest discover -s tests -v`
  是有效的：GitHub runner 默认无 `DISPLAY`，`env -u` 能显式移除；测试里的
  `Typer` 全部被假后端或 Mock 替换，不会连接 X。✅
- `discover -s tests` 会把 `tests/` 插入 `sys.path`，因此 `from support
  import ...` 可用；`python -m unittest` 同时保留 cwd，`import autopaste`
  也可用。✅
- 矩阵保留 `check` 的 3.9–3.13，`tests` 取 3.9/3.13，成本合理；没有为了
  绿灯删除或跳过既有检查。但见 M2（缺 3.8）。
- `package` job 只验证 `--version`，不验证元数据版本、LICENSE 内容、也不是
  在无 X 库环境下运行；对「打包正确性」的覆盖偏薄（m2）。
- 测试依赖 runner 预装的 `libX11`/`libXtst`（import 时加载），但既有
  `check` job 的 `python autopaste.py --version` 同样依赖，故不是本任务新
  引入的断点；显式 `apt-get install` 会更稳，但不是本次必须。

### 5. 安全默认未被放宽

- 本任务对 `autopaste.py` 的 diff 为 0（`w1mer show 01` 只有 tests/、
  pyproject、CI、README），root 拒绝、控制字符拦截、FIFO/设备拒绝、终端
  多行确认、1 MiB 输入上限的**实现**均未改动。✅
- 但新增的安装入口使 SECURITY.md §2 #9（SIGINT/SIGTERM/SIGHUP + atexit
  双保险）在 `pip`/`pipx` 安装形态下失效，见 M1；这是本次唯一的安全契约
  退步。
- 安全相关的测试覆盖：root/控制字符/FIFO/上限都有反例；**终端多行确认
  （SECURITY.md #4）零测试**，`_confirm()` 无 tty 时拒绝的路径也未测（m6）。

### 6. 文档一致性

- README.md 的安装（`pipx install .` / `./install.sh`）、测试
  （`python3 -m unittest discover -s tests -v`）、版本单一来源说明与实际
  能力一致。✅
- README.en.md 未同步：仍只有 `./install.sh`，没有 pipx/pyproject、没有开发
  测试章节，中英文文档出现能力差异（m1）。
- CHANGELOG 仍只有 1.0.0，未提工程化基线（可留给任务 05 的 1.1.0，n2）。
- README「零依赖」指无 PyPI 依赖，但 import 即加载系统 X 库，属既有表述，
  非本次改动。

## Findings

### Major

- **M1 安装后的入口绕过信号处理，削弱 SECURITY.md #9 的还原承诺。**
  `pyproject.toml` 的 `autopaste = "autopaste:main"` 让 console script 直接
  调用 `main()`；而 `_install_signals()` 只在 `autopaste.py:946-947` 的
  `if __name__ == "__main__"` 分支调用（`main` 定义在 `:817`，信号函数在
  `:936`）。安装形态下 `__name__ == "autopaste"`，SIGTERM/SIGHUP 采用默认
  行为，进程立即终止，`atexit` 不执行，`Typer.close()` 不会还原临时键位
  映射。文档明确写「SIGINT/SIGTERM/SIGHUP 与 atexit 双重兜底」「异常/
  Ctrl-C/SIGTERM 时都会还原」，因此这是安装入口引入的真实契约退步。
  现有测试/CI 捕获不到：`package` job 只跑 `--version`（在创建 Typer 之前
  退出），也没有入口级信号测试。
- **M2 `requires-python >= 3.8` 无 CI 背书。** 元数据、classifier、README
  都承诺 3.8，但 `check` 矩阵从 3.9 起，`tests` 仅 3.9/3.13。静态看代码
  应兼容（future annotations + 无运行时 3.9+ 语法），但这是未被验证的
  承诺；应在 ubuntu-22.04（或可用镜像）加 3.8 测试，或把元数据/文档统一
  提升到 3.9。
- **M3 `test_dry_run_exits_zero` 是假绿。** `tests/test_cli.py:62` 只断言
  退出码 0 和输出包含 `dry-run`；`Typer` 被整体替换为 `MagicMock`，却从未
  断言 `typer.type_text` / `typer.press` 未被调用。哪怕 dry-run 分支在
  return 前误调用了注入方法，测试仍通过——而这正是 SECURITY.md #5 要保证
  的核心行为（不发任何 XTEST 事件）。
- **M4 remap 测试无法捕获「还原早于按键」的时序回归。**
  `FakeX11.mapping_history` 与 `FakeXtst.events` 是两条独立列表，没有共享
  时间线。`test_unicode_remap_and_restore`（`tests/test_typer.py:63`）断言
  remap[0]、restore[-1] 和按键序列分别正确；如果实现把
  `_restore_keymap()` 移到 `_tap()` 之前，两条列表仍然都会通过，但实际会
  输出错误字符。它能捕获漏还原/异常不还原，不能验证「先 remap、再按键、
  后还原」这一必须成立的顺序。
- **M5 超限粘贴测试把 off-by-one 固化为契约，且未验证剩余字节。**
  `tests/test_lineeditor.py:82` 断言返回 `payload[:limit + 1]`，而生产代码
  （未改动侧）`_read_paste` 的循环是 `while len(data) <= MAX_PAYLOAD`，确实
  会多读 1 字节；测试把这个实现细节写成期望。后果：若后续按「读到终止符
  后截断到 MAX_PAYLOAD」正确修复，测试反而失败。测试也没有断言被截断后
  管道里剩余字节如何消费（测试数据在截断点后没有换行/控制字符，因此无法
  发现剩余内容被当作普通按键重新读入）。SECURITY.md #10 声称括号粘贴缓冲
  受 1 MiB 限制，这条测试没有把「限制 + 剩余输入处理」定义清楚。

### Minor

- **m1 README.en.md 未同步**：安装仍只有 `./install.sh`，没有
  `pipx install .`、pyproject、测试命令；中英文文档能力不一致。
- **m2 LICENSE/版本元数据缺少校验，且 license 写法已弃用**：
  `license = { file = "LICENSE" }` 在 setuptools ≥77 是 deprecated（未来
  移除），`requires = ["setuptools>=61"]` 无上界；CI 不检查 wheel 内
  LICENSE、也不比较 `pip show autopaste` 的版本与 `__version__`。建议改
  PEP 639 `license = "MIT"` + `license-files = ["LICENSE"]`，并加一条
  `python -c "import importlib.metadata..."` 的版本一致性断言。
- **m3 `test_resolvable` 近乎恒真**：`tests/test_typer.py:142` 在
  `spare_kc` 存在时两个输入都返回 `[]`，没有覆盖 `spare_kc is None` 的
  分支、也没有覆盖多字符缺失顺序；实现永远返回 `[]` 也能通过。
- **m4 `test_delay_attribute`（`:146`）是重言式**，只证明构造函数把
  `delay=0.0` 存下来了，没有验证 `type_char` 实际使用该延时。
- **m5 `test_esc_preview` 的截断断言过弱**：`assertIn("6", out)` 可能匹配
  到别处的数字；应断言完整后缀（如 `共 6 字符`）或精确输出。
- **m6 终端多行确认路径零测试**：`warn_terminal_target()`、`_confirm()`
  以及非 tty 默认拒绝（SECURITY.md #4）没有用例；`main()` 的终端目标分支
  也没有 CLI 级测试。
- **m7 `test_root_rejected`（`tests/test_cli.py:68`）未 mock `Typer`**：
  该用例只 patch `geteuid`。一旦 root 闸门回归且开发者在真实 X 会话跑测试，
  代码会继续进入 `Typer` 并可能真的注入 `hi`；在 CI 无 X 时只是变成另一个
  失败码。属测试卫生问题，建议同样 patch `autopaste.Typer` 并断言未构造。
- **m8 wheel 平台标签是 `py3-none-any`**，而项目实际仅支持 Linux/X11；
  本地安装无碍，若发布到 PyPI 会误导非 Linux 用户。属打包元数据 nit。

### Nit

- **n1** `tests/support.py` 的 `redirect_std(monkey_targets=None)` 参数从未

- **n2** CHANGELOG 1.0.0 未记录本任务的 pyproject/tests/CI；可由任务 05 的
  1.1.0 一并补，不单独修。
- **n3** `test_oversized_paste_truncated` 的名称/注释说「截断」，实际期望
  是 `limit+1` 字节，名称与契约不符（与 M5 同源）。
- **n4** `test_close_is_idempotent` 只断言 `XCloseDisplay` 一次，未断言
  `_restore_keymap` 的 `XSync`/flush；低风险。

## 架构影响说明

- **生产代码零改动**：本任务没有为可测性新增接口/依赖注入层。测试 seam 是
  既有的模块级 `autopaste.x11` / `autopaste.xtst` 全局对象，用
  `mock.patch.object` 替换即可；对单文件 CLI 而言这是**恰当的最小接缝**，
  没有引入不必要的 Backend 抽象（那是任务 02 的范围）。
- **契约移动**：项目从「单脚本」变成「可安装包」——模块名 `autopaste`、
  console entry `autopaste:main`、版本号唯一来源 `autopaste.__version__`；
  CI 新增 `tests`/`package` 两个 job，测试套件成为回归基线。
- **新暴露的耦合**：模块 import 时即 `ctypes.CDLL` 加载 `libX11`/`libXtst`，
  所以「安装后哪怕只跑 `--version`」也要求系统有这两个库；这是既有加载
  方式，但打包后才成为用户可见的安装前提，README/SECURITY 应继续把它写成
  X11 运行要求。
- **入口分叉**：脚本路径（`__main__`）与安装路径（console script）对
  `_install_signals()` 的处理不一致（M1）；应统一到一个入口函数，避免
  「脚本安全、安装后不安全」的双轨契约。
- **测试假后端的局限**：FakeX11/FakeXtst 各自记录历史，无法表达跨后端的
  时序（M4）；后续需要「同一事件日志」才能验证 remap/restore 与按键的
  相对顺序。这是测试基础设施的演进点，不是生产复杂度。
